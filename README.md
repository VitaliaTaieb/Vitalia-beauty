# VITALIA Beauty

Наявний сайт двох салонів: Vitalia Beauty (Кфар-Йона) і Vitalia Taieb (Нетанія).
Клієнтська сторінка — івритом, адміністративний кабінет — українською та івритом.

## Запуск і розгортання

`index.html` та `admin.html` — статичні сторінки GitHub Pages.
Серверні функції розгортаються окремо в наявний проєкт Supabase `nsazdqspilhjdtdkjgwg`.
Публікація HTML через Pages сама по собі **не оновлює** серверні функції.

Перед оновленням функції звірте її код із розгорнутою версією.
Ця зміна відновлює в репозиторії функції версії 8 із робочого проєкту,
зберігаючи персональні посилання, перенесення, святкові дні та паузи після процедур.
Додатково клієнтська сторінка й сервер відхиляють процедури з `import_only=true`:
вони призначені для збереження старих імпортованих записів, а не нових бронювань.

Серверні змінні:

| Змінна | Призначення |
| --- | --- |
| `SUPABASE_URL` | URL наявного проєкту |
| `SUPABASE_ANON_KEY` або `SUPABASE_PUBLISHABLE_KEY` | Перевірка користувача в адмін-функції |
| `SUPABASE_SERVICE_ROLE_KEY` або `SUPABASE_SECRET_KEYS.default` | Привілейований доступ сервера до бази |
| `TURNSTILE_SECRET_KEY` | Перевірка Cloudflare Turnstile під час бронювання |

Секретні ключі й паролі не можна додавати в HTML або Git. Publishable key та Turnstile site key у HTML публічні.

## Вхід адміністратора

1. `admin.html` надсилає email і пароль до Supabase Auth (`token?grant_type=password`).
2. Access token, refresh token та строк дії зберігаються у `localStorage.vitalia_admin_session`.
   Код застосунку не зберігає пароль. Токени доступні JavaScript цього домену, тому захист від XSS обов'язковий.
3. Перед запитом та раз на хвилину `ensureSession()` перевіряє строк дії; за 90 секунд до завершення
   обмінює refresh token. Web Locks, якщо доступні, координують оновлення між вкладками.
4. Адмін-запити передають `apikey` і `Authorization: Bearer <access_token>`.
5. `vitalia-admin` викликає `auth.getUser(token)` і вимагає `user.app_metadata.role === 'vitalia_admin'`.
   Звичайна реєстрація та `user_metadata` не надають прав адміністратора.
6. Лише після перевірки прав сервер використовує секретний ключ бази. Роль дає доступ до обох салонів.
7. Вихід викликає Supabase logout і видаляє локальну сесію; інші вкладки реагують на подію `storage`.

У `supabase/config.toml` обидві функції мають `verify_jwt=false`, як у поточному розгортанні:
публічна функція допускає бронювання без реєстрації, а адмін-функція самостійно перевіряє користувача та роль.
Не видаляйте цю перевірку з обробника адміністратора.

## Клієнтське бронювання

Клієнт обирає салон, його процедуру, дату й час та проходить Turnstile.
Сервер повторно перевіряє робочі години, ручні закриття, свята й перерви.
Зарезервований інтервал включає процедуру та паузу після неї.
Перевірка зайнятості охоплює обидва салони; наявне обмеження бази `appointment_no_overlap`
також захищає від одночасних запитів. Його не слід видаляти.

Для перегляду створюється випадковий токен із 32 байтів. База отримує лише SHA-256 хеш.
Клієнт отримує токен один раз, зберігає до 30 токенів у `localStorage.vitalia_my_bookings`
і може відкрити посилання `#booking=<token>`. Запит `my_booking` знаходить запис за хешем;
знання номера телефону або ID бронювання не дає доступу. Власник особистого посилання може переглянути запис.

## Перевірки

Node.js 22.13+:

```sh
node --test tests/booking.test.mjs
```

16 перевірок виконують справжній код обробників із підставленими базою та Turnstile.
Охоплюють особисті токени, права адміністратора, обидва салони, святкове перевизначення,
перерви, сумарну тривалість і помилку накладки від бази. Це не перевірка реального CAPTCHA або живого запису.

Для браузерного сценарію встановіть Playwright 1.62.1 та Chromium:

```sh
npm install --no-save playwright@1.62.1
npx playwright install chromium
node tests/browser.cjs
```

Можна вказати наявний браузер через `CHROMIUM_EXECUTABLE`.
Сценарій перевіряє клієнтське бронювання, розділені меню, приховування імпортних процедур,
перегляд запису, збережений вхід, оновлення токена, іврит і вихід на ширинах 390 та 820 px.
API та Turnstile в ньому підставлені; реальні записи не створюються.

## Межі підтвердження

На 22 листопада 2026 року: 16 серверних перевірок пройшли локально.
Живий endpoint доступності повернув успішну відповідь; адмін-endpoint без токена повернув 401.
Браузерні перевірки на ширинах 390 і 820 px пройшли в GitHub Actions (run 44958679430):
бронювання в обох салонах, особистий запис, збережений вхід, оновлення токена, іврит та вихід.
Локальний запуск Chromium заблокований середовищем; CI виконав цей сценарій із підставленими API.
Вхід із реальними обліковими даними, реальний Turnstile та повне бронювання на сайті не перевірені.

Автоматичне надсилання WhatsApp **не активоване**: у базі є згода й черга нагадувань,
але потрібні підключення провайдера, погоджений шаблон і відправник. Згода у формі не означає, що повідомлення вже надсилаються.
